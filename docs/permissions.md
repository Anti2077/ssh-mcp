# 三档操作权限

每个 SSH 目标、数据库实例分别设置操作权限。在 `ssh-mcp manage` 中编辑目标，找到“操作权限”，用 `← / →` 选择并“验证并保存”。权限是本地配置，MCP 工具不能更改权限或批准操作。

| 档位 | 明确识别的读取 | 修改、脚本、未知操作、提权 | 文件部署 |
| --- | --- | --- | --- |
| 只读巡检 `read_only` | 自动执行 | 拒绝，零派发 | 拒绝 |
| 确认后操作 `confirm`（默认） | 自动执行 | 本地管理界面逐次确认 | 确认源文件 SHA-256、目标和启动动作后执行 |
| 完全授权 `full` | 自动执行 | 无需逐次确认 | 无需逐次确认 |

新目标和升级前的现有目标均默认 `confirm`。升级不会自动授予完全权限。改变权限会更新目标 revision，使旧的会话和待确认请求失效。建议生产服务器使用只读巡检，测试服务器按需要选确认后操作。

## 确认流程

1. MCP 提交具体请求，daemon 校验目标、凭据、黑名单和固定规则。
2. 需要确认时，daemon 保存一条仅在内存中存在的待确认请求，并打开本地管理界面。
3. 界面显示目标、配置版本、完整命令/SQL、是否提权、会话目录及环境、输出/时间预算。部署额外显示源路径、大小、SHA-256、远端路径和启动动作。
4. 默认选择“拒绝”。长内容可用 `↑ / ↓` 滚动；查看到最后一页后，`Tab` 选择“允许本次操作”，`Enter` 提交。`Esc` 拒绝。终端控制字符和双向文字控制符会转义显示。
5. 允许只对正在等待的本次调用生效。再次调用、改变命令、改变上下文或改变目标均不能复用确认。执行前重新检查目标 revision 和凭据状态。

确认窗口最长等待两分钟，也受客户端调用超时限制。拒绝、取消调用、关闭管理界面、客户端主体退出、凭据锁定或超时均不派发操作。客户端不支持打开本地终端时，请自行运行 `ssh-mcp manage`；仍需在超时前完成确认。管理界面打开失败时请求直接拒绝，准备好界面后由用户重新发起请求。

部署在确认前创建权限为 `0600` 的本地临时快照，确认绑定该快照的 SHA-256；确认后修改原文件不会改变上传字节。结束后删除快照；daemon 意外崩溃可能留下临时快照，应按敏感文件处理。

MCP 没有 `approve` 工具、确认令牌参数或 `confirmed=true` 字段。AI 不得自己操作管理界面代替用户确认，也不得在拒绝后换工具、改写命令或切换系统 SSH 以达到相同效果。

## 只读巡检识别范围

SSH 采用保守的正向识别：常见的 `ls`、`cat`、`head`、`tail`、`grep`、`stat`、`wc`、`pwd`、`whoami`、`id`、`uname`、`uptime`、`free`、`df`、`du`、`ps` 等，以及受限的 `systemctl status/show/... --no-pager` 和 `journalctl --no-pager` 查询。

支持这些读取命令之间的普通管道和 `&& / ||`。重定向、变量/命令替换、赋值、自定义环境、脚本/解释器、未知语法和提权不视为可自动执行的读取。比如 `free -m` 可直接执行，`sudo free -m`、`sh -c 'free -m'` 和 `python3 check.py` 需要确认档/完全授权。`read_ssh_file` 提供独立的受限普通文件读取入口。

数据库读取沿用 SQL 分类和数据库只读事务；可能写入的 SQL 需要 `confirm/full` 和已配置的可写账号。数据库用户、函数及扩展也应由管理员限制权限。

## 所有档位保留的边界

- 已登记并启用的目标、凭据库解锁、SSH 主机指纹验证。
- SSH 目标命令黑名单；专用文件 API 还要求“允许文件读写”。只读巡检下该开关不授予部署权限。
- 当前 daemon 能识别的格式化、原始块设备写入、基础系统目录破坏、无界资源耗尽、危险 SQL、未登记远端跳转等硬拦截。
- 输出/时间/并发限制、显式会话上下文和本地审计。远端结果未知不自动重试。

`opaque_shell_effect` 在只读巡检仍启用；确认档/完全授权允许脚本和解释器，不再因此一律硬拦截。其他可识别的硬拦截仍适用。例如直接 `rm -rf /usr` 仍拒绝，但静态规则无法证明任意 Python/Bash 脚本内部的全部行为。三档权限不是远端 OS 沙箱；完全授权仍受远端登录账号权限限制。不要把黑名单、静态分析或提示词当作对恶意本机程序的防护。

## Codex 自带审批

Codex 的工具审批是额外一层，不替代 daemon 的本地确认。工具列表中 `list_targets`、`describe_target_capability`、`list_databases`、`read_ssh_file` 标注 `readOnlyHint=true`；通用 `run_ssh`、`execute_ssh_session`、`run_sql` 和部署工具保留可能修改的语义。

在现有 Codex 配置的 `[mcp_servers.ssh-mcp]` 段内按需设置：

```toml
default_tools_approval_mode = "writes"
tool_timeout_sec = 1200
```

`writes` 要求客户端对未标注只读的工具执行审批；`prompt` 要求每次调用审批。实际由谁审批还受 Codex 的全局审批设置及组织策略影响，不能保证每个 MCP 调用都由真人审批。`tool_timeout_sec` 给本地确认和最长部署留出时间，daemon 自身仍应用每个操作的时间上限。不要重复添加同名 TOML 表。参考 [Codex 配置说明](https://developers.openai.com/codex/config-reference/)。

在对话里写“写入前问我”可以改善 AI 行为，但不能构成服务端授权。选择 `confirm` 后，客户端自动批准工具调用也不会替代本地用户的确认。
